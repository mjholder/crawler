## What I worked on

Implemented the **fixed-sequence enemy pattern system** spec'd in [[ideas.md]]
("Enemy Attack Patterns", 2026-06-30). Enemies can now run an ordered, looping list
of moves — each carrying the same reusable `Effect` subclasses that drive player
attacks/spells — instead of a single hardcoded behavior.

- New resources: `EnemyMoveData` (`scripts/enemy_move_data.gd`) — name, description,
  `Target` enum (`PLAYER`/`SELF`), `effects[]`, icon, sound; and `EnemyPatternData`
  (`scripts/enemy_pattern_data.gd`) — an ordered `moves[]` list.
- `Enemy` (`scripts/enemy.gd`): optional `pattern` export + per-instance
  `_pattern_index` cursor, a `move_performed` signal, `peek_next_move()` (telegraph
  read), and a pattern-aware `_emit_attack()` that falls back to the legacy
  `attack(attack_damage)` when no pattern is set. Because `_emit_attack()` is the
  single emission seam (Skeleton's `.tscn` fires it via an animation method track),
  **Skeleton needed no code changes** — attaching a pattern just works.
- Effect application mirrors the player path: `move_performed` flows
  `Enemy → CombatEvent → game._on_enemy_move_performed()`, which resolves the target
  (player, or the enemy itself for SELF moves) and applies each effect. Damage still
  routes through `player.take_damage` (DEF mitigation + HP bar), and `enemy_attack_hit`
  is re-emitted for damage-bearing player moves so equipment retaliation procs still fire.
- Content-editor: registered both classes in `export_schema.gd` + `annotations.json`,
  regenerated `schema.json` (now MCP-authorable). Authored a sample loop via the MCP
  pipeline — `Wind Up → Heavy Swing → Guard` (small / big / self-DEF-buff) under
  `resources/enemy_moves/` + `resources/enemy_patterns/`, attached to a new inherited
  scene `scenes/skeleton_skirmisher.tscn`, wired into the `debug_combat` example event.

### Dropped (decided this session)

## Key decisions made

Logged in [[design.md]]: patterns are **data-driven and optional**, additive to the
`_perform_action()` override hook (bosses/conditional AI still override); `_emit_attack()`
is the emission seam; targeting is enemy-centric (`PLAYER`/`SELF`); enemies lack a full
stat block so move `DamageEffect` expressions must use literals or `max_health`/`health`,
not `strength`-style terms.

## Blockers / struggles

- Enemies only expose `DEFENSE` as a base stat (`_get_base_stat`) — STR/CON/etc. evaluate
  to 0 in `StatExprEval`, so enemy damage expressions are constrained to literals/health.
  A future enemy stat block would lift this; out of scope here.
