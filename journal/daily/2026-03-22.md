## Key decisions made

- Equipment is a **Node with a Resource for data** — the Node owns sprites, animation, and audio; the `EquipmentData` resource holds stat modifiers, `SpriteFrames`, and audio streams. One scene per equipment type, swap the resource for a different item.
- **Modifier layer** for stats — Player base stats stay as `@export` floats; `get_effective_stat()` sums base + equipment modifiers at calculation time. No direct stat mutation on equip/unequip.
- **Shared `Enums` class** (`scripts/enums.gd`) holds `Stat` and `Slot` enums. Neither Player nor Equipment owns them. Turn state and other game-wide enums can migrate here over time.
- **Weapon is reactive, not an actor** — Player owns all attack logic. Weapon connects to Player's `attack` signal and plays its own animation and SFX in response.
- **Signal-based wiring** — Player's `equip()` method connects/disconnects the `attack` signal when items are swapped. Consistent with the existing signal-based separation pattern.

## Follow-up session (same day) — player visual cleanup

Realised the player scene has no `Sprite` and no `AnimationPlayer`. The design doc assumed the player had its own attack animation, but that's now entirely delegated to the weapon. Updated both scripts to reflect this.

### What changed

**`scripts/player.gd`**
- Removed `_sprite` (`AnimatedSprite2D`) `@onready` reference
- Removed `_sprite.animation_finished.connect()` from `_ready()`
- Removed `State.HIT` — no sprite means no hurt animation to track; hurt feedback is SFX + overlay flash only
- Removed `_transition(State.HIT)` from `take_damage()`; removed all sprite calls from `_transition()`
- Removed `_on_sprite_animation_finished()`
- Added `_attack_animation_pending: bool` flag — set to `true` in `_do_attack()` when a weapon is equipped
- `_is_turn_complete()` now blocks while `_attack_animation_pending` is true — turn doesn't end until the weapon animation finishes
- `equip()` now wires/unwires `(item as Weapon).anim_player.animation_finished` → `_on_weapon_animation_finished` alongside the existing `attack` signal connection
- Added `_on_weapon_animation_finished()` — clears `_attack_animation_pending`

**`scripts/weapon.gd`**
- Renamed `_anim_player` → `anim_player` (removed underscore) so `player.gd` can reference it for signal wiring

### Key decision

The `attack` signal fires when the player decides to attack and damage is calculated. The weapon's `animation_finished` signal is what gates turn completion — the turn ends when the visual is done, not when the number is computed. This keeps damage calculation and animation timing decoupled without adding any new signals to `Weapon`.

## Follow-up session (same day) — sprite scaling crash fix

Hit a crash on startup: `Invalid access to property 'sprite_frames' on a base object of type 'null instance'` from `game.gd:_scale_sprite_to_viewport()`. The call in `_ready()` was trying to get a `"Sprite"` child from the Player node, but the player scene has no Sprite — the visual is entirely the weapon.

### What changed

**`scripts/equipment.gd`**
- Added `_scale_sprite_to_viewport()` helper — reads `get_viewport_rect().size`, gets the "idle" frame 0 texture, computes a proportional scale factor, applies it to `_sprite`
- `_on_equipped()` now calls `_scale_sprite_to_viewport()` — fires automatically whenever any equipment is equipped, regardless of context

**`scripts/game.gd`**
- Removed the broken `_scale_sprite_to_viewport($Player.get_node("Sprite"))` call from `_ready()`
- `_scale_sprite_to_viewport()` remains in `game.gd` — still used for enemy sprites

### Key decision

Scaling lives in `Equipment` rather than `game.gd` — equipment owns its own presentation. Any weapon or item equipped anywhere will size itself correctly without the caller needing to know about it.

## Follow-up session (same day) — debug weapon resource loading and animation fixes

Picked up after the scene was built in the editor. Got the battle axe showing and animating correctly end-to-end.

### What changed

**`scripts/game.gd`**
- Gated the weapon equip block on `debug_start_combat` (was firing independently)
- After instantiating the weapon scene, preloads `resources/equipment/weapons/battle_axe.tres` and assigns it to `weapon_instance.data` before `equip()` is called — `Equipment._ready()` reads `data` on tree entry so timing is correct

**`resources/equipment/weapons/battle_axe.tres`**
- Changed attack animation `loop` from `true` to `false` — `AnimatedSprite2D.animation_finished` only fires for non-looping animations, so the turn was never ending

**`scripts/weapon.gd`**
- `_on_player_attacked` was calling `anim_player.play("attack")` — the AnimationPlayer had no animations defined, so it silently did nothing and `animation_finished` never fired
- Switched to driving `_sprite` (AnimatedSprite2D) directly: `_sprite.play("attack")`
- Added `signal animation_finished` on Weapon as a clean no-param hook for player.gd
- Connected `_sprite.animation_finished` internally in `_ready()` — handler re-emits `animation_finished` and returns to idle
- Fixed handler signature: `AnimatedSprite2D.animation_finished` emits zero parameters, but the handler was declared with `anim_name: StringName`, causing Godot to silently drop the connection. Changed to no-param and check `_sprite.animation` instead

**`scripts/player.gd`**
- Updated `equip()` connect/disconnect to use `weapon.animation_finished` instead of `anim_player.animation_finished`
- Dropped `_anim_name: StringName` param from `_on_weapon_animation_finished`

### Key decision

Rather than building AnimationPlayer animations in code (complex) or in the editor (requires separate setup), the attack flow now drives the AnimatedSprite2D directly. The `AnimationPlayer` stays in the scene for future multi-phase sequences but isn't in the basic attack path. `Weapon.animation_finished` is the stable signal player.gd cares about — the sprite wiring is an internal detail.

### Lessons

`AnimatedSprite2D.animation_finished` takes no parameters in Godot 4. Connecting it to a function with a `StringName` param silently fails — no error, no warning, just nothing. Worth checking signal signatures whenever a handler never fires.

## Follow-up session (same day) — enemy health bar positioning fix

Health bars for enemies were all rendering at screen position (0, 0) because `add_enemy_health_bar` in `gui.gd` added bars as children of `_enemy_hud` with no position set.

### What changed

**`scripts/gui.gd`**
- Added `@export var enemy_health_bar_offset: Vector2 = Vector2(0, -40)` — editable on the GUI node in the Godot editor, controls how far above (or offset from) the enemy world position the bar appears
- In `add_enemy_health_bar()`, position is now set once at creation time: `get_viewport().get_canvas_transform() * enemy.global_position + enemy_health_bar_offset`
- Static placement is sufficient because fights don't involve enemy movement

### Key decision

The offset lives in `gui.gd`, not `enemy.gd` — it's a display concern, not game logic. A single shared export covers all enemies for now; if different enemy types need different offsets, revisit.

### Notes

`get_canvas_transform().xform()` doesn't exist in Godot 4 — the replacement is the `*` operator: `transform * vector`. `xform()` was a Godot 3 API.
