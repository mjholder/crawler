## Key decisions made

- **Builder view pattern for floor slots**: floor slots are inline sub-resources inside `DungeonFloorData`, not standalone files. Rather than a file list, the sidebar entry opens a focused builder that picks a floor file and exposes only its `slots` array. Reuses the existing generic FieldRenderer machinery, so reactive visibility applies for free.
- **`FIELD_VISIBILITY` / `FIELD_DIR_OVERRIDES` registry pattern**: per-class predicates in `fieldVisibility.ts` keep FieldRenderer generic. New classes (or new overrides) can be added without touching the renderer. `FIELD_DIR_OVERRIDES` is the same idea for resource-typed fields where the natural `api.listType(cls)` call would return nothing.

## Blockers / struggles

- Event classes (`CombatEventData`, `BossEventData`, etc.) all extend `Resource` directly with no shared base — `api.listType("Resource")` finds nothing. Required the dir-scan approach rather than schema-based class resolution.
- `WeightedEntry` has no explicit discriminant field (unlike FloorSlot's `type` enum) — the "which branch is active" question is answered by whether `event` is null. The visibility predicate uses a null-check on the field value itself rather than a separate type field.
