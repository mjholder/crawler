## What I worked on

Content-migration pass following the Phase 17 weapon-anatomy work ([[daily/2026-07-31]]). Audited
all 11 weapons, their attacks, and the referenced effects to confirm `power`/`scaling` reach every
basic attack. Findings and fixes:

- **`skull_bash.tres`** (the mace's bash) was still on the baked inline expression `strength * 0.5`,
  bypassing the mace's authored `power 24 / scaling 0.4`. Rewritten to ratio form
  `power + scale * scaling` (K = 1.0 baseline; tunable). The `apply_stun` payload is untouched.
- **Unarmed** now flows through the system. `_UNARMED` is a bare `AttackData` used as the empty-hand
  fallback — there was no `WeaponData` to carry `power`/`scaling`, so the ratio form would have
  evaluated to 0. Created `resources/equipment/weapons/fists.tres` (a real `WeaponData`:
  `power 0 / scaling 0.3 / STR`, attacks = the Punch). `player.gd` now backs the empty-hand punch
  with this innate Fists weapon in `weapon_context_for` (new `_FISTS` const + `_weapon_context_from`
  helper), and `unarmed_damage.tres` became `power + scale * scaling`. Verified numerically identical
  to the old `strength * 0.3` (4.2 at STR 14).
- **`apply_bleed.tres`** (the rapier's `rend` — its *only* effect, so this is rend's front hit, not a
  proc) was hardcoded to `agility * 0.5`, bypassing the rapier's `power 8 / scaling 0.6 / AGI`.
  `GatedBleedEffect` already forwards `context`, so migrated the immediate-hit expression to
  `power * 0.5 + scale * scaling` — a reduced K, since rend's payoff is the bleed DoT, not the hit.
  The bleed **status** itself (`bleed.tres`, flat `1`/tick, `bypass_armor`) stays flat — that's real
  status damage, correctly outside the weapon knob.
- **Deleted the chop orphans** — `resources/attacks/chop.tres` and `resources/effects/chop_damage.tres`
  (`"20 + (strength/2)"`) were referenced by nothing (battle_axe uses `cleave`), dead since "v1 tool".

Then promoted the per-attack coefficient into a real, buffable knob (the numbers like `power * 1.2`
were the *only* remaining literals in the weapon expressions):

- **`AttackData.power_coefficient`** (default 1.0) + a new **`coeff`** var in `StatExprEval` (its
  absent-default is 1.0, since it multiplies). Every weapon damage expression collapsed to the single
  uniform form `power * coeff + scale * scaling`. Per user call, all attacks are **flattened to K=1.0**
  (moves now differ via pierce/status/cooldown/crit/buffs, not baked raw damage) — so no per-attack
  `.tres` authoring was needed, just the field default.
- **Buffable, additively *and* multiplicatively.** `StatusData` gained `coefficient_add` /
  `coefficient_mult`; `Combatant.get_attack_coeff_add()` (Σ) / `get_attack_coeff_mult()` (Π) aggregate
  active statuses; `weapon_context_for` resolves `coeff = (power_coefficient + add) * mult` per hit.
  New `AttackCoeffBuffEffect` (`Mode { ADD, MULTIPLY }`) authors either kind as a `stack_decays` status,
  mirroring `BuffEffect`. This is the player-facing "buff my damage" lever the design wanted.
- **Preview stays legible**: `humanize_expression` hides `coeff` at 1.0 (`20 + STR × 0.5`) and surfaces
  it once buffed (`20 × 1.3 + STR × 0.5`), so an active buff is visible on the tooltip/overlay.
- Verified: headless import clean; a test confirmed `power * coeff + scale * scaling` evaluates
  27 / 33 / 37 at coeff 1.0 / 1.3 / 1.5, the humanizer hides-then-shows coeff, and the additive×mult
  composition `(1.0+0.3)*1.5 = 1.95` is correct.

## Key decisions made

- **Unarmed gets a real `WeaponData` (`fists.tres`)** rather than staying a legacy stat expression —
  so bare hands go through the identical `power + scale * scaling` path as every weapon. Fists aren't
  equippable, so the context is read from the base (no upgrade/rarity/tags to compose). See
  [[ideas/weapon-anatomy-power-and-scaling]].
- **All weapon attack hits are uniform with the system** — including bundled hits like rend's, whose
  damage lives inside a `GatedBleedEffect`. Only genuinely non-weapon damage stays stat-based:
  spells, self-costs, and status DoTs.

## Authoring surfaces — default the ratio form, tweak the variables

Propagated the settled damage form (`power * coeff + scale * scaling`) into every authoring surface so
new content is created on the uniform expression and authors tweak the *variables*
(`power`/`scaling`/`scaling_stat` on the weapon, `power_coefficient` on the attack) instead of writing
raw stat formulas:

- **Content-editor schema** (`tools/content_editor/schema.json`) regenerated from Godot. Now carries
  `AttackData.power_coefficient`, `StatusData.coefficient_add`/`coefficient_mult`, and the new
  `AttackCoeffBuffEffect` class + its `Mode` (ADD/MULTIPLY) enum. Registered
  `attack_coeff_buff_effect.gd` in `export_schema.gd`'s `RESOURCE_SCRIPTS` + `ENUM_SCRIPTS` (it was
  missing from the allowlist, so the class never exported). The frontend form editor is schema-driven,
  so these fields now render automatically. **Note:** the running MCP server caches schema.json at
  startup — a server restart (or next session) is needed for its `get_schema` to reflect the new fields.
- **Linter** (`sidecar/src/linter.ts`) — added the weapon-anatomy vars `power`, `scaling`, `scale`,
  `coeff` to `ALLOWED_VARS`. Before this, a correctly-authored `power * coeff + scale * scaling` would
  have been flagged as four unknown variables. Verified: ratio form lints clean, a `powr` typo still
  errors, spell/stat expressions still allowed.
- **MCP authoring doc** (`docs/mcp-authoring.md`) — expanded the allowed-vars line and added a
  "Weapon damage expressions — use the uniform form, tweak the variables" section.
- **`create-weapon` skill** — questionnaire now asks for the weapon's `power`/`scaling`/`scaling_stat`
  (new Group 4) and the per-attack `power_coefficient` shape knob; all `.tres` templates (DamageEffect,
  both AttackData templates, WeaponData) switched from `strength * 0.5` to `power * coeff + scale * scaling`
  + the anatomy fields; added a standalone `AttackCoeffBuffEffect` template.

## Bugfix — empty-hand punch dealt 0 damage

Field-testing exposed that the bare-handed Punch previewed as the raw expression
`power * coeff + scale * scaling` and dealt **0 damage**, despite `fists.tres` carrying real
`power`/`scaling`. Root cause was a live logic bug in `player.weapon_context_for`, not the numbers:

- An empty hand still registers `_UNARMED` into that hand's moveset (`_build_hand_actions`, the
  `data == null` fallback). So `_weapon_slot_owning_attack(_UNARMED)` returns a **real** slot
  (WEAPON/OFFHAND), never `-1`.
- That routed the context lookup into the equipped-weapon branch, where `get_equipped_instance(slot)`
  is `null` for an empty hand → `return {}`. The `slot == -1` Fists fallback was therefore **dead
  code** and never ran. With an empty context, `power`/`scale`/`scaling` all default to 0.

Fixed by keying the branch on "is there a backing weapon *instance*?" instead of the slot lookup:
resolve the equipped `ItemInstance` first (or `null` when `slot == -1`); use it if it's a
`WeaponData`, else fall back to innate `_FISTS` when the attack is `_UNARMED`, else empty. The Fists
fallback is now reachable for empty hands.

Also tuned the Fists numbers off the `power = 0` placeholder to `power = 4 / scaling = 0.5 / STR`
(0.5 matches the axes' scaling for consistency), so the punch is a real floor (`4 + STR × 0.5`:
9 at STR 10, ~16.5 at STR 25) rather than pure STR scaling. Headless import clean.
