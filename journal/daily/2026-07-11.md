## What I worked on

Reformatted the player UI. Added a status effect container to the player UI — placeholder for where active status icons will live. Already have a status effect sprite sheet ready to use.

Then reconciled `gui.gd` with the restructured HUD and built the status-icon plumbing. The HUD rework had nested nodes into group Controls (`PlayerHealth/`, `PlayerArmor/`, `PlayerGold/`, `PlayerXP/`, `PlayerMagic/`) but `gui.gd` still used the old flat `@onready` paths, so those refs were broken/null. Fixed the paths, wired mana to the scene's new `PlayerMagic` bar/label (was previously built in code at an offset that now overlapped the health group), and kept `_player_status_label` alive but demoted it to a transient toast for `show_status()` messages (e.g. "Not enough mana"), repositioned clear of the layout.

For status icons: rewrote `refresh_player_statuses()` to rebuild an icon strip in `CombatHUD/PlayerStatusEffects/StatusContainer` — one `TextureRect` per active status built in code (no per-status scenes, unlike the world-map nodes), reading `StatusData.icon`. All from the single `status-sheet.png` atlas.

Then consolidated poison and reworked stacking to intensity-based. Deleted `minor_poison`/`strong_poison` (+ their `apply_*` wrappers); there's now one `poison` status/icon, strength = stack count. Changed `StackPolicy.STACK` semantics: instead of appending parallel instances, re-applying now bumps a `stacks: int` on the single existing `StatusInstance` and refreshes duration (`combatant.apply_status`). `DamageEffect.apply_tick` (and `BurstDamageEffect`) multiply tick damage by `stacks`, so a status ticks **once per turn** for `base × stacks` — not N separate ticks. This applies to bleed/burn too (both STACK + plain `DamageEffect`). The status icon shows the stack count as a corner number (only when >1); tooltip shows name/stacks/turns. Attacks apply stacks by listing the `apply_poison` effect N times: flail = 1, assassinate = 3. Stacks persist through save/load.

Then a HUD polish pass on the resource bars: magic label dropped its `MP` prefix to plain `xx/xx` (matches health); wired the scene's `PlayerXPBar` (it was never referenced by `gui.gd`, so it sat stuck at its editor default `50.0`) and reworked `update_player_xp(current, to_next)` to drive both bar and label with progress toward the next level; armor bar now stays visible at `0/0` for no-DEF builds instead of hiding. All variable-max bars use `max_value = maxf(maximum, 1.0)` to avoid a degenerate `0/0` ProgressBar range. Finally fixed the warrior armor bar loading at a base-stat value (`4–7`) then jumping to `73` in combat: `set_player` runs before `initialize()` equips gear, so the armor refresh had to move to `_enter_world_map` (post-init, shared by new-run and continue) where `refresh_armor()` fills the buffer to the fully-equipped DEF.

Set up an **editor-time combat-UI preview**: authored dummy content directly into `scenes/game.tscn` so the CombatHUD renders populated in the Godot editor (no need to run through the full flow to see it). Added 3 dummy `Button`s under each of `MainhandActions`/`OffhandActions`, two `health_bar.tscn` instances under `EnemyHUD` (with the `Armor` sub-node overridden `visible = true` for the armor overlay), and sample `text`/`value` on the PlayerHUD health/armor/mana/gold/xp nodes. No script changes — the runtime already clears all of it before real combat: `gui.gd:_ready()` hides the CombatHUD, `_populate_hand_group()` frees the action rows before rebuilding, and `hide_event_hud()` (via `_enter_world_map`) frees the enemy bars. So the dummies are purely a design-time scaffold and never leak into a run. Verified via headless instantiate: 3+3 buttons, 2 bars, armor visible, HUD labels updated, scene loads error-free.
