## Key decisions made

- `DialogueEvent` emits `dialogue_requested(data)` in `_on_running()` rather than passing data through a setter — keeps the event self-contained and consistent with the signal-based event pattern.
- `_on_gui_dialogue_complete()` restores `_pre_dialogue_state` before calling `on_dialogue_complete()`, so the turn state is clean before `event_complete` fires and `_finish_event()` sets it to `NO_TURN`.
- `_advance_phase()` in the base class handles RUNNING → RESOLUTION → COMPLETE atomically, so `_on_resolution()` doesn't need an override in `DialogueEvent` — nothing to resolve yet.
- Return-to-menu on `_finish_event()` rather than per-event — all events share the same cleanup path so the behavior is consistent.
- `CombatEvent` overrides `_advance_phase()` to stop at RESOLUTION — the base class's synchronous RESOLUTION→COMPLETE chain would have fired `event_complete` before an `on_victory` dialogue could display. `_on_resolution()` decides whether to wait or advance directly.
- Enemy instantiation moved into `CombatEvent._on_setup()` (scoped ownership), but positioning and sprite scaling stay in `game.gd` via the `enemy_added` signal — those operations need `screen_size` which lives in game.gd.
- `on_dialogue_complete()` public method pattern (from `DialogueEvent`) reused for `CombatEvent` — game.gd calls it after victory dialogue to advance to COMPLETE.
